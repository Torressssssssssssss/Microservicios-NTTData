TAREA 1 - TC-01: ACTUALIZACION REACTIVA DE INGREDIENTES
==============================================================================

Problema original:
El PUT devolvia void y descartaba repo.save(). Un publisher reactivo describe
una operacion; descartar el publisher no ejecuta la escritura. Una diferencia
entre ID de ruta y cuerpo producia una excepcion interna, no un error 400.

Solucion:
PUT /api/ingredients/{id} devuelve Mono<ResponseEntity<Ingredient>>.
Mono.defer aplaza validacion y acceso al repositorio hasta la suscripcion.
Se exige que el ID del cuerpo coincida con la ruta, incluyendo rechazo de ID
nulo. Nombre no vacio y tipo son obligatorios. Se consulta existencia antes de
guardar. La escritura pertenece al flatMap de la cadena que recibe Spring.

Contrato:
200: ingrediente actualizado en el cuerpo JSON.
400: identidad inconsistente, nombre vacio, tipo ausente o JSON invalido.
404: ingrediente inexistente; no se guarda ni se crea un documento.
No se agregan block(), subscribe() ni metodos void para ejecutar esta operacion.

Pruebas:
Estados 200/400/404 mediante MockMvc y despacho asincrono del Mono.
StepVerifier comprueba emision y finalizacion.
Una escritura simulada con Mono.defer comprueba ausencia de efecto antes de la
suscripcion, ejecucion posterior y una sola invocacion de save.
La prueba de integracion comprueba el cambio por GET contra MongoDB real.

TAREA 2 - TC-02: ELIMINACION REACTIVA DE INGREDIENTES
==============================================================================

Problema original:
El DELETE era void y descartaba repo.deleteById(), por lo que no garantizaba
el efecto ni diferenciaba recursos ausentes.

Solucion:
DELETE /api/ingredients/{id} devuelve Mono<ResponseEntity<Void>>.
Busqueda, error de ausencia y eliminacion estan encadenados. thenReturn genera
la respuesta solo al finalizar deleteById. No hay try/catch sincronico.
GET por ID tambien devuelve 404 si falta el ingrediente, para que se pueda
observar la desaparicion y seguir el contrato de los retos.

Contrato:
204 sin cuerpo cuando termina la eliminacion.
404 si el ID no existe, incluyendo una segunda eliminacion del mismo ID.
La operacion es idempotente: repetirla no cambia el efecto final, aunque el
estado HTTP de la segunda respuesta sea diferente.

Pruebas:
El repositorio simulado cambia un indicador de presencia al suscribirse.
Se verifica 204, cuerpo vacio, efecto terminado, GET posterior 404, segundo
DELETE 404 y exactamente una eliminacion. ID ausente no invoca deleteById.
Se agrega tambien una prueba de persistencia real en IngredientMongoIT.

TAREA 3 - TC-03: LOCATION BASADO EN LA PETICION
==============================================================================

Problema original:
El POST construia http://localhost:8080/ingredients/{id}; faltaba /api y se
fijaban host, puerto y esquema independientemente de la peticion.

Solucion:
POST /api/ingredients recibe Ingredient y HttpServletRequest en el runtime
Spring MVC del proyecto. ServletUriComponentsBuilder.fromRequestUri captura
la URI antes de entrar en la cadena reactiva. Tras guardar, pathSegment agrega
el ID realmente devuelto por persistencia y encode protege segmentos de URI.
No se concatena un URL completo ni se utiliza el ID anterior a persistencia.
Se valida nombre y tipo antes de guardar. Se responde 201 con cuerpo y Location.
El controlador ya no contiene la referencia literal localhost:8080.

CORS:
El origen permitido se mueve a taco.api.allowed-origin en los application.yml
del modulo API y de la aplicacion. El valor inicial conserva el origen del
proyecto: http://localhost:8080. No se abre CORS para cualquier origen.

Proxy:
En despliegue detras de un proxy confiable, utilizar
--server.forward-headers-strategy=framework
para que Spring procese Forwarded/X-Forwarded-* antes de construir Location.
El proxy debe controlar esos encabezados. No se habilita confianza global en
encabezados de clientes directos como parte de este cambio.

Pruebas:
URI con HTTPS, host distinto, puerto 9443 y context path /course.
ID asignado por persistencia distinto del de entrada y GET siguiendo Location.
Encabezados X-Forwarded-Host, X-Forwarded-Proto y X-Forwarded-Prefix mediante
ForwardedHeaderFilter en MockMvc.
Body invalido produce 400 sin escritura.
La prueba de integracion utiliza servidor MVC con puerto aleatorio y /course.

TAREA 4 - TC-04: PATCH CONTROLADO DE ORDENES
==============================================================================

Problema original:
Se recibia TacoOrder completo, se permitia cambiar pago, faltaba autorizacion
y deliveryZip se tomaba incorrectamente de deliveryState.

Solucion:
PATCH /api/orders/{orderId} recibe OrderPatchRequest, no TacoOrder.
Lista blanca: deliveryName, deliveryStreet, deliveryCity, deliveryState,
deliveryZip. Los campos omitidos o nulos no se modifican. No hay reflection
ni copia masiva de propiedades. JsonAnySetter rechaza campos desconocidos,
incluso si su valor es null: no hay descarte silencioso de campos protegidos.
OrderService consulta, autoriza, aplica los campos explicitamente, valida el
resultado y realiza una unica escritura. ZIP se copia de deliveryZip.
Los cinco datos de entrega resultantes deben ser no nulos y no vacios.

Autorizacion:
Authentication debe estar autenticado y no ser AnonymousAuthenticationToken.
Solo el propietario identificado por username o una autoridad ROLE_ADMIN
puede modificar la orden. No se acepta userId ni usuario en el body.
Ordenes sin propietario solo pueden modificarse por ADMIN.

Contrato:
200: orden actualizada.
400: campo prohibido, JSON invalido o datos de entrega resultantes vacios.
403: usuario ajeno o peticion sin identidad autenticada.
404: orden ausente. Se mantiene la busqueda antes de la comprobacion de acceso.

Pruebas:
ZIP y estado se modifican independientemente.
Rechazo de id, user, placedAt, total, status, ccNumber, ccExpiration, ccCVV,
tacos, incluyendo null. Validacion de ZIP vacio.
Propietario, usuario ajeno, ausencia de autenticacion, ADMIN y recurso ausente.
Se verifica ausencia de save en rechazos y una escritura por cambio valido.

TAREA 5 - TC-05: IDENTIDAD, REEMPLAZO Y ELIMINACION DE ORDENES
==============================================================================

Problema original:
El PUT ignoraba el orderId de la ruta y guardaba el dominio del cuerpo.
El DELETE descartaba el publisher y usaba try/catch para una operacion asincrona.
No habia comprobaciones de propietario ni estado de la orden.

Solucion de PUT:
PUT /api/orders/{orderId} recibe OrderReplaceRequest con @Valid.
El ID opcional del cuerpo debe coincidir con la ruta cuando se proporciona.
Un ID omitido utiliza la identidad de la ruta. La orden debe existir.
Solo se reemplazan los cinco datos de entrega y la lista de tacos.
Se requieren datos de entrega no vacios y lista de tacos no vacia; se validan
las restricciones existentes de Taco mediante @Valid.
Se conservan ID, usuario, placedAt, status y los tres datos de pago existentes.
Campos protegidos o desconocidos producen 400, no se copian a persistencia.
Se exige propietario o ROLE_ADMIN igual que en PATCH.
200 al guardar; 400 por entrada invalida; 403 por acceso ajeno; 404 por ausencia.
PUT no crea ordenes nuevas. No se calcula precio ni se incorpora TC-14.

Solucion de DELETE:
DELETE /api/orders/{orderId} compone busqueda, autorizacion y deleteById.
Devuelve 204 sin cuerpo solo al terminar el efecto; 403 por acceso ajeno,
404 por ausencia y 409 cuando el estado no permite eliminacion fisica.

Estado minimo necesario:
TacoOrder agrega Status con CREATED, PREPARING, READY, DELIVERED y CANCELLED.
Las ordenes nuevas inician en CREATED. Las antiguas con estado null se tratan
como CREATED para esta comprobacion, sin exigir migracion inmediata.
Solo CREATED/null admite eliminacion fisica, incluso para ADMIN.
PREPARING, READY, DELIVERED y CANCELLED producen 409. No se implementa aun el
workflow de estados ni cancelacion distribuida: corresponden a TC-25.
Los DTOs de PUT/PATCH no permiten que el cliente cambie este estado.

Pruebas:
ID contradictorio, ausencia, usuario ajeno, reemplazo valido y preservacion de
identidad, usuario, fecha, estado y pago. Rechazo de pago y body incompleto.
DELETE ausente, ajeno, anonimo, PREPARING/READY/DELIVERED/CANCELLED con propietario y ADMIN, CREATED con
204 tras el efecto y orden antigua sin estado con ADMIN.

LIMITES Y DECISIONES

La configuracion general de seguridad sigue siendo la del baseline, con rutas
permitAll y contrasenas sin proteccion adaptativa. TC-10 y TC-11 quedan fuera
del alcance. El servicio protege PUT/PATCH/DELETE aun con esas rutas abiertas:
sin Authentication valido responde 403. POST, GET y correo conservan su contrato
original y deben endurecerse en los retos posteriores.
User del baseline solo concede ROLE_USER. La rama ADMIN del servicio soporta
ROLE_ADMIN y se verifica con una identidad de prueba; asignar roles reales
corresponde al trabajo posterior de seguridad.
POST original no asigna automaticamente un propietario. Para pruebas manuales
de ordenes debe existir una orden con user consistente; si user falta, el
servicio no concede acceso como propietario.
PUT/PATCH siguen devolviendo TacoOrder del baseline. No se resuelve todavia la
exposicion de datos sensibles del dominio: corresponde a TC-08 y TC-12. No usar
PAN/CVV reales. Las pruebas solo emplean valores sinteticos.
Busqueda y escritura no son una transaccion atomica. No se agrega optimistic
locking ni workflow: una carrera concurrente entre estado y eliminacion debe
resolverse al evolucionar TC-25. Este cambio verifica el estado observado.
La compatibilidad de ordenes antiguas sin estado supone que eran CREATED; en
una migracion productiva se debe revisar esa suposicion.
No se afirma que pasen los navegadores Angular, los brokers ni todo el reactor
Maven: la validacion ejecutada se centra en API y sus modulos dependientes.
